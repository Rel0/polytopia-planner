# Tile terrain model

The Market planner fills in the terrain of unmarked tiles from the screenshot. This runs fully in the
browser (`js/tilemodel.js`, no API key, nothing is uploaded). The model itself is a small random forest
in `js/tilemodel-data.js`, generated by `export.py`.

## Features (`feat.py`, ported 1:1 to `js/tilemodel.js`)

For each tile, 14×14 points are sampled in two places: the tile diamond, and the column above it
(trees, mountains and buildings rise above their tile). Each region gives 21 numbers: a 12-bin hue
histogram, pale/grey/dark shares, mean and std of brightness, mean saturation, texture, and the share
of points inside the image. That makes 42 features in total.

If you change `feat.py`, change `js/tilemodel.js` the same way. Then check that both give the same
predictions on all labelled tiles (they did: 1633/1633).

## Collecting labels (Label tool)

Open the app with `?label` in the URL (e.g. `https://polytopiaplanner.com/?label`). A 🏷️ **Label** tool appears.
1. Load a screenshot and confirm the grid. Use ½ or 2× if the diamonds are the wrong size.
2. Every tile shows the model's guess (yellow; orange outline means unsure). Pick a brush and tap the wrong tiles:
   - terrain sets the terrain
   - Crop / Fruit / Metal / Animal / Fish and **Unit on it** toggle extras
   - buildings toggle
   - Skip is for tiles hidden by the game's UI
3. **Export labels (.json)** downloads one file per screenshot: the image, the grid and every tile's label.
   Collect these files in a folder.

```sh
python3 tools/tilemodel/from_labels.py ~/labels /tmp/tiledata        # → /tmp/tiledata/dataset.json
python3 tools/tilemodel/export.py /tmp/tiledata/dataset.json js/tilemodel-data.js
```

## Retraining

The training screenshots and labels are **not** in this repo. Game screenshots stay local. The
dataset file looks like this:

```json
[{ "img": "/path/shot.png", "grid": { "w": 132.3, "cx": 361.9, "cy": 771.8 },
   "tiles": [{ "x": 410.2, "y": 812.5, "label": "forest+animal" }] }]
```

Labels are `field`, `forest`, `mountain`, `water`, `city`, `village`, `cloud`, `edge`, `space`,
`farm`, optionally followed by `+resource`. Tiles marked `ui` or `skip` are left out. `(x, y)` is the
tile centre and `w` is the tile width, as found by `PP.vision.detectGrid`.

```sh
python3 tools/tilemodel/export.py dataset.json js/tilemodel-data.js   # needs numpy, pillow, scikit-learn
```

## Accuracy (v2, Nov 2026)

Training data: 1,215 hand-labelled tiles from 16 screenshots (about 12 tribes; 85 tiles with a unit), plus
automatically labelled cloud and space tiles.

Measured leave-one-screenshot-out. Almost every screenshot shows a different tribe, so each test is mostly
"a tribe the model has never seen":

| | v1 model | v2 model |
|---|---|---|
| land tiles (field / forest / mountain / water / city) | 58 % | 80 % |
| land tiles with a unit on them | 47 % | 78 % |
| tiles with confidence ≥ 0.6 (57 % of land tiles) | | 93 % |

Resources (v2):

| | all | sure (≥ 0.7) |
|---|---|---|
| metal on mountains | 93 % | 98 % (55 % of mountains) |
| crop / fruit on fields | 75 % | 99.5 % (35 % of fields) |

The app fills in a resource only when the model is sure about it.

The ring features are what helps with units: a unit covers the centre of its tile, while the outer band of the
diamond stays visible. More screenshots per tribe, labelled with the Label tool, are the biggest lever from here.

## Crop (v3, Nov 2026)

Crop shows up as many small light sprouts on a field. Their shape and colour differ per tribe. The 14 × 14 lattice of
the tile features was too coarse for them: only 28 of 124 crop fields were found at the 0.7 the app used.

`feat.crop_features` adds 14 numbers from a fine lattice over the tile diamond. It counts specks that are lighter
or darker than their neighbours and little peaks along each row. It also measures how even the ground is and what
colour the specks have. Only the field model uses these features, in `js/tilemodel.js` (`cropFeatures`); the terrain
and mountain models are unchanged.

Crop on fields, leave-one-screenshot-out (124 crop fields, 402 other fields):

| | found | wrongly called crop |
|---|---|---|
| v2, threshold 0.7 (old) | 28 | 4 |
| v3, threshold 0.6 (`CROP_SURE`, used) | 81 | 5 |
| v3, threshold 0.7 | 57 | 0 |

## City detector (v3, Nov 2026)

Every city, own or enemy, has a **name plate** centred on its tile: white italic text with a dark shadow on a
half-transparent box in the tribe colour (own cities also have a light progress bar). Villages have no plate. The old plate finder in
`js/vision.js` only searched the colours of tribes whose units had already been detected, so it missed most plates
(6 of 48 labelled cities).

`city.py` trains a separate detector (extra trees) on the 62 tile features plus 26 plate features
(`feat.plate_features`, ported 1:1 to `PP.tilemodel.plateFeatures`). The plate features work like this:
- A fine lattice is sampled around the tile centre.
- The row with the strongest white "strokes" is found, and everything else is measured from there: shadow, colour,
  text width and centring, the box edges above and below, and the progress bar.
- So a plate a little higher or lower looks the same to the model.

`detectCities` runs it on every tile of the grid. A city only counts where its tile beats all 8 neighbours,
because a plate also reaches into the tiles next to it. The top and bottom game UI is skipped.

```sh
python3 tools/tilemodel/city.py dataset.json,dataset_city_extra.json js/citymodel-data.js
```

The extra file holds cities and non-cities that were checked by hand. The 8 neighbour tiles of every city are added
as non-cities. Big cities rise into the tile above, and without these negatives that tile could win the neighbour
check, so the city ended up one tile too high.

Leave-one-screenshot-out, 61 cities on 25 screenshots. The neighbour check is done like in the app, including the
neighbour tiles:

| threshold | cities found | false alarms (of 1520 other labelled tiles) |
|---|---|---|
| 0.45 | 54 / 61 | 9 |
| 0.5 (used) | 50 / 61 | 4 |
| 0.6 | 46 / 61 | 2 |

On the training screenshots, 59 of 61 cities land on the right tile and none is a tile too high.

Python and the browser give the same plate features: 377 of 377 tiles. Both compute the plate HSV in float64 and
the row smoothing in the same order.
